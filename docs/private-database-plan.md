# Private Database + CKShare Plan

**Status: planned, not started.** Option 3 from the security review that produced #61 (removing `_world` read) and #62 (sanitizing untrusted text). This doc is the design record and the decision log; nothing here is implemented yet.

Target release: **2.0.0**. See [Versioning](#versioning).

## Why

#61 closed anonymous read of the public database. Verified behaviourally: a CloudKit Web Services query with a valid API token now returns `ACCESS_DENIED` where it previously returned every `Pair` record with its `pairKey` in plaintext.

What that did **not** close: CloudKit's public-database security roles are per record type with no row-level scoping, so `_icloud` — every signed-in Apple ID — still has read *and write* on `Pair`, `Alert`, and `Ack`. Two consequences remain:

- Any authenticated client that can reach the container can read every pair's records, `pairKey` included.
- Any such client can write records into any pair. #62 bounds how that renders (sanitizing names, messages, and the ack emoji at every parse boundary), but it does not stop the writes.

What makes this narrow in practice is that `CKContainer(identifier:)` traps without the iCloud container entitlement, and Apple issues that only to the owning team — verified under both team-signed and true ad-hoc signing (issue #60). So there is no easy native client for a stranger to build. The residual paths are a leaked token or a jailbroken device running the real app.

Moving pair data into the **private** database, shared between the two devices with `CKShare`, replaces "no row-level scoping" with per-zone access controlled by CloudKit itself. That is the actual fix rather than a mitigation.

## The risk that has to be settled first

**Push delivery is the app's core property and the mechanism changes. Verify this before writing the rewrite.**

Today, alerts arrive as a *visible* APNs push generated by a `CKQuerySubscription` on the public database with `shouldSendMutableContent = true`. That is what lets `NotificationService` (the NSE) intercept, fetch the real record, and render a banner with the sender's name — **even when the receiving app has been force-quit or the phone is locked**. For an app whose entire purpose is "my partner needs to know right now," that property is the product.

Under a private/shared database this is genuinely uncertain, in three separate ways:

1. **Does `CKQuerySubscription` work in the shared database at all?** Query subscriptions are documented for private and shared databases, but the semantics for a *participant* observing changes in a zone owned by someone else are the part I have not confirmed.
2. **Are visible (alert) pushes permitted there?** The `Ack` record type exists today purely because CloudKit's public-DB query subscriptions reject `firesOnRecordUpdate` combined with a mutable-content alert push (see CLAUDE.md). That restriction was justified by the public database's broad write permissions, so it may not apply here — but "may not" is not "does not."
3. **Is `CKDatabaseSubscription` the only supported option, and is it silent-only?** If the shared database forces `CKDatabaseSubscription` + `CKFetchRecordZoneChangesOperation`, and that path only ever delivers `content-available` pushes, then **there is no NSE-rendered banner any more**. The app would have to wake in the background and schedule a local notification — which iOS does not guarantee to deliver promptly, and does not deliver at all if the user force-quit the app.

Outcome 3 would be a serious regression in the app's reliability, and it is the plausible one. It has to be settled with a spike before committing to this design, not discovered halfway through a rewrite.

**Spike, before any production code:** a throwaway branch that creates a zone in the private database, shares it with a second iCloud account, registers whatever subscription types are accepted, and confirms on a real device whether a banner appears with the app force-quit. Nothing else in this plan is worth building until that answer is in hand.

If the answer is "no visible push," the options are to accept degraded delivery, keep a minimal public-database record purely as a push trigger carrying no content (a hybrid that keeps some exposure), or abandon Option 3 in favour of Option 2 (encrypting payloads under a `pairKey`-derived key). That decision belongs to whoever reads the spike result.

## A possible simplification, if the risk resolves well

If visible pushes *are* permitted on record update in a shared zone, the `Ack` record type can be deleted entirely. It exists only as a workaround for the public-DB restriction, and it costs a second write per acknowledgement plus a record type that is never garbage-collected. The sender-side banner would come from the `Alert` update directly. Worth checking during the spike since it is nearly free to test at the same time.

## Versioning

**2.0.0.** Every release since 1.0.0 has been drop-in; this is the first requiring manual user action and breaking install-to-install compatibility:

- `PairState` (`attention.pair.v1` in UserDefaults) becomes meaningless — the `pairKey` no longer addresses anything. Every existing user must re-pair.
- The invite payload changes from `attention://pair?k=…&id=…&n=…` to an iCloud share URL. A 1.7 device cannot read a 2.0 invite, or the reverse. This also supersedes part of `remote-pair-sharing-plan.md`, whose whole premise is that the QR is just a transport for that custom-scheme URL.
- Alerts move databases, so a 1.7 device and a 2.0 device are invisible to each other.

`CURRENT_PROJECT_VERSION` stays at `1` as always — Xcode Cloud assigns the build number at archive time.

## Decisions

### Mixed-version window: hard cutover with explicit UI

Two phones update independently, so there is a window where one partner is on 2.0 and the other on 1.7. In that window, pressing the button must not silently do nothing — a silent delivery failure is worse than an error for this app.

2.0 drops public-database support outright. On first launch it invalidates the existing pair and prompts re-pairing; until the partner has also updated and accepted the share, the UI says so plainly rather than appearing to work. The pair is non-functional for that window, which for a two-person app means one QR scan in the same room.

Rejected: a dual-mode release reading and writing both models. It keeps the public database live and readable for the entire transition — the exact exposure being closed — and doubles the CloudKit code paths while both exist.

### Ownership asymmetry

Today pairing is symmetric: one scan and both sides can send and receive. `CKShare` introduces an owner (the inviter, whose private database holds the zone) and a participant. Capability stays symmetric if the participant has read-write, but ownership does not, and that has consequences worth naming up front:

- If the owner deletes the app or signs out of iCloud, the shared zone goes with it. The participant loses everything. There is no equivalent failure today.
- Anything that assumes symmetry — `PairState`, the pairing UI copy, `deletePair` — needs revisiting.

### History migration: read early, and the sequencing problem

Decision: preserve pre-2.0 history rather than dropping it. But "migrate on first launch" cannot be taken literally.

There is one shared zone, owned by the inviter, and ownership is decided at *re-pair* time — after first launch. Both devices can read the same old public `Alert` records, so if each migrates them into its own zone, they duplicate once shared.

The read must happen at first launch regardless, before the public grants are revoked, so **that part is common to both readings and can be built first**. What happens to the cached records afterwards is the open choice:

- **Local snapshot, merged at display.** Each device keeps its own copy; `HistoryView` shows local-old plus shared-new. No duplication possible, no ordering dependency. Old history stops syncing between devices.
- **Replay into the zone after pairing.** The zone owner writes its cached records into the shared zone, deduped by original `recordName`. True continuity, but needs idempotency and a defined winner when the two snapshots differ.

Recommendation: the local snapshot. For ping-and-ack records, a per-device snapshot is indistinguishable from synced history in practice and removes a class of dedupe bugs. **Not yet decided.**

## Surface that changes

`CloudKitService` is roughly fifteen methods, every one of them against `publicDB`:

| Area | Today | Under Option 3 |
| --- | --- | --- |
| Pairing | `createPair` / `fetchPair(pairKey:)` / `joinPair` — a queryable `pairKey` lookup | Create a zone, `CKShare`, accept via `CKAcceptSharesOperation` |
| Alerts | `sendAlert` / `markAlertSeen` / `acknowledgeAlert` on `publicDB` | Same shapes against the shared zone |
| History | `fetchRecentAlerts(pairKey:)` — predicate on a queryable field | Zone-scoped fetch; `pairKey` predicates disappear |
| Subscriptions | Four `CKQuerySubscription`s keyed on `pairKey` (`SubscriptionPredicates`) | Whatever the spike establishes |
| NSE | Fetches the `Alert` by record ID from `publicDB` | Must reach the shared zone from the extension |
| Schema | `cloudkit-schema.ckdb`, three public record types | Private-DB record types; the `_icloud` grants stop being the control |

Also affected: `PairState` (new shape), `SubscriptionPredicates` (largely obsolete), `AppState.bootstrap` (the DEBUG `schema-seed` dance is public-DB-specific), `SETUP.md` §CloudKit, and `Tools/AttentionCLI` (already broken — issue #60 — and this decides whether it is repaired or deleted).

Probably unaffected: the watch, which never talks to CloudKit and goes through `WatchBridge`.
