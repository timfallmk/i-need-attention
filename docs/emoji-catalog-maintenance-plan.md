# Emoji Catalog Maintenance Plan

How to keep `App/Helpers/EmojiCatalog.swift` from going stale as Unicode adds new emoji.

## Why

The in-app acknowledgement picker (`EmojiPickerView` + `EmojiCatalog`) is backed by a hand-curated Swift literal: ~1000 codepoints across 9 categories, plus a keyword index for search. Apple ships no public API that vends categorized emoji or English keywords (the system keyboard is a private input view), and the available Swift packages are middling — so we authored the dataset ourselves.

Unicode adds roughly 50–100 emoji per year (Unicode 15.0 → 15.1 → 16.0 → 17.0 → …), each tied to an iOS release. Without a maintenance step, those new emoji render correctly anywhere the system handles them but never appear in our picker. The system keyboard, being part of iOS, picks them up automatically; our static list does not.

Acceptable as-is for a personal-use app — the existing entries keep working forever, and missing the newest 50 emoji per year only matters if a user specifically reaches for one. We chose to keep the catalog current with a generator script (the bump procedure below); deferring to the system keyboard is recorded further down as the alternative we did *not* take.

## The bump procedure (do this when a new Unicode emoji set ships)

`Tools/generate_emoji_catalog.py` reads Unicode's `emoji-test.txt` and rewrites `App/Helpers/EmojiCatalog.swift` — categories, the search keyword index, `fitzpatrickBase`, and a header comment recording the upstream version. A vendored snapshot of the source data lives at `Tools/data/emoji-test.txt` so regenerations are reproducible and diffs are reviewable.

New Unicode emoji versions land roughly yearly and ship to users in a matching iOS update. When that happens:

```sh
# 1. Refresh the vendored snapshot from upstream (the "latest" symlink).
curl -o Tools/data/emoji-test.txt https://unicode.org/Public/emoji/latest/emoji-test.txt

# 2. Regenerate the Swift from the vendored snapshot.
python3 Tools/generate_emoji_catalog.py --data Tools/data/emoji-test.txt

# 3. Review the diff — both files together.
git diff Tools/data/emoji-test.txt App/Helpers/EmojiCatalog.swift
```

If `git diff` is empty, the catalog already matches the latest published set — there's nothing to bump (Unicode hasn't released a new version since the last run). That's the expected outcome most of the time; don't manufacture a commit.

If there's a diff, sanity-check that the new emoji landed in sensible categories, then commit the snapshot and the regenerated `.swift` together with a message noting the Unicode version (e.g. "Bump emoji catalog to Unicode 18.0").

Notes:

- Run `python3 Tools/generate_emoji_catalog.py` with no `--data` to fetch `latest` directly instead of vendoring first, or add `--dry-run` to print the Swift without writing it. The two-step "vendor then regenerate from the snapshot" flow above is preferred because it keeps the committed `.swift` reproducible from a committed input.
- The header comment in `EmojiCatalog.swift` (`// Generated by … — Unicode Emoji <version>`) is the quickest way to see which set the checked-in catalog reflects.
- `emoji-test.txt` is Unicode's source-of-truth list; the picker's English keywords are derived from each emoji's name in that file. (Richer keyword sources like [emojibase](https://github.com/milesj/emojibase) exist, but the derived keywords have been good enough, so the generator stays dependency-free on Python's standard library.)

## Alternative we didn't take — defer to the system keyboard

Drop the in-app grid entirely. Replace `EmojiPickerView` with a sheet that auto-focuses an empty `TextField` and prompts the user to tap an emoji on the system emoji keyboard. Take the first emoji grapheme cluster from the field's contents as the ack.

**Sketch:**

```swift
struct EmojiPickerView: View {
    let onPick: (String) -> Void
    @State private var text = ""
    @FocusState private var focused: Bool

    var body: some View {
        VStack {
            TextField("Tap an emoji", text: $text)
                .focused($focused)
                .onChange(of: text) { _, new in
                    if let emoji = new.first(where: { $0.unicodeScalars.first?.properties.isEmoji == true }) {
                        onPick(String(emoji))
                    }
                }
        }
        .onAppear { focused = true }
    }
}
```

(`UITextInputMode` lets us nudge the keyboard to start in emoji mode if we want; otherwise the user toggles it.)

**Trade-offs:**

- "Any emoji" becomes literally any emoji the user's iOS supports. No catalog. No staleness.
- Zero data maintenance forever.
- UX is plainer — no categorized grid, no in-app search. Users with the system emoji keyboard hidden behind ABC have an extra tap.
- Loses a bit of the Tapback-like polish the curated row plus grid implies.

## Status

Decided: the generator is in place and the categorized grid stays. The catalog currently reflects **Unicode Emoji 17.0** (see the header comment in `EmojiCatalog.swift`). Maintenance is the bump procedure above — run it when a new Unicode emoji set ships in an iOS release; expect it to be a no-op in years when Unicode hasn't published a new version.

Revisit the system-keyboard alternative only if the categorized grid stops earning its keep — i.e. if we'd rather trade the in-app search and visual polish for zero data maintenance.
